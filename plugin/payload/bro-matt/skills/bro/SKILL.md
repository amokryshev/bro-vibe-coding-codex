# bro

Ты координируешь поручение пользователя и навыки Matt Pack. Работаешь по явному обращению к bro: например, `$bro` в Codex или `/bro` в Claude Code. Тип результата определяет поручение: исследование заканчивается выводами, программная задача — проверенными изменениями; сложность сама по себе не разрешает расширить объём.

## 1. Проверь и подготовь контекст проекта

При каждом вызове, включая пустой `$bro`, используй следующий порядок. Если пользователь явно запросил полную ревизию кода и контекста, сразу переходи к [порядку полной ревизии](references/project-context-review.md), независимо от возраста документов и прошлой проверки. Иначе, если в текущей сессии для этого проекта уже была успешная быстрая проверка, используй её результат без повторного чтения документов, проверки дат и сверки кода. Для другого проекта или новой сессии проведи быструю проверку.

Определи фактический корень проекта и прочитай действующие `AGENTS.md`/`CLAUDE.md`, чтобы установить пути обязательного комплекта:

| Документ | Содержание |
| --- | --- |
| `docs/research/composition-overview.md` | Компоненты, входы, интерфейсы, данные, зависимости, запуск и тестирование |
| `CONTEXT.md` | Основные понятия проекта с ясными значениями |
| `docs/agents/domain.md` | Расположение словаря и ADR, правила их чтения и ведения |
| `docs/agents/issue-tracker.md` | Выбранный трекер, проект или место локальных задач, правила операций |

Пути могут отличаться по явным соглашениям проекта; установи соответствие каждому пункту. Дополнительно учитывай документы, обязательные по этим соглашениям, включая `docs/agents/triage-labels.md`, если используется triage. Исторические ADR не обязаны обновляться ежемесячно: проверяй актуальные документы контекста, а не каждый файл под `docs/`.

**Быстрая проверка** ограничена наличием файлов, отсутствием пустого шаблона или незаполненных обязательных разделов и датой обновления. Упоминание TODO в примере кода или явно описанный открытый вопрос не является заглушкой документа. Код с документами на этом этапе не сверяй, тесты и исследование архитектуры не запускай.

Дату бери из принятой проектом явной отметки актуализации; при её отсутствии — из последнего Git-коммита, изменившего документ. Для файла без Git-истории используй filesystem mtime и укажи этот источник. Неизвестную или будущую дату считай непроверенной. Сравнивай с датой на один календарный месяц раньше сегодняшней в часовом поясе проекта; если такого дня в прошлом месяце нет, используй его последний день. Дата ровно на границе допустима. Сам факт проверки, checkout или копирования не является основанием обновить дату в документе.

Выбери исход:

- **Всё в порядке:** каждый обязательный документ присутствует, не является заглушкой и обновлён не более месяца назад. Сохрани в текущем диалоге проект, дату проверки, пути и результат; продолжай поручение. До конца этой сессии автоматическую проверку этого проекта не повторяй. Этот результат не означает, что код прошёл полную ревизию.
- **Есть документы старше месяца:** сообщи пользователю конкретные файлы и даты и предложи полную ревизию кода и актуализацию контекста. Запускай её только после явного запроса или согласия. Возраст документа сам по себе не блокирует поручение; пока ответа нет, продолжай работу, которая от ревизии не зависит. Отказ не означает, что документы стали свежими.
- **Обязательных документов вообще нет:** сразу начни полную ревизию по [отдельной инструкции](references/project-context-review.md), чтобы создать контекст. Для её старта дополнительное подтверждение не требуется. Наличие одного лишь `project.md` или пустого каталога `docs/` не считается наличием комплекта.
- **Комплект частичный, содержит заглушки или непроверенные даты:** перечисли конкретные пробелы, предложи адресное восстановление; полную ревизию автоматически не запускай. Если одновременно есть старые документы, сообщи и об этом, предложив полную ревизию. Уточняй только существенные неизвестные, независимую работу продолжай. Полный комплект пустых шаблонов относится к этому случаю, а не к полному отсутствию файлов.

Сохраняй также уже показанные предупреждения и ответ пользователя: повторный вызов в той же сессии не должен заново предлагать отвергнутую или ожидающую ответа ревизию. После согласованного восстановления проверь только затронутые пункты; при успешном результате используй его до конца сессии. Явная просьба пользователя перепроверить контекст отменяет повторное использование прошлого результата.

Настройка bro для текущего агента находится в `../../bro-vibe-coding/project.md` относительно этого `SKILL.md`. Прочитай её для параметров, не заданных общими документами проекта. Она помогает подготовке, но не заменяет обязательный комплект. Общие инструкции проекта имеют приоритет; настройка другого агента не является условием работы.

Проверь только возможности, нужные для текущего шага. Используй доступные средства host и выбранный проектом трекер: внешний сервис или локальные Markdown-задачи. Название установленного MCP не определяет способ работы. Авторизация внешнего сервиса и разрешение на конкретное действие проверяются фактическим результатом; файл конфигурации этого не доказывает. Недоступность сервиса, не нужного для поручения, не блокирует независимую работу.

Если проектные соглашения неполны, восстанови известное из файлов и диалога. Существенные неизвестные решения уточняй, а создание документов при автоматически начатой полной ревизии выполняй в её границах. Полную ревизию веди через конкретные навыки Matt Pack по [маршруту ревизии](references/project-context-review.md): `research` для обзора, затем `grill-with-docs`/`domain-modeling` для понятий и решений, `setup-matt-pocock-skills` для соглашений. Применяй workflow каждого нужного навыка, а не только упоминай его название. Быстрая проверка эти навыки не запускает. Сохраняй пользовательские материалы. Установка и настройка плагина выполняются его штатным lifecycle; это отдельное действие пользователя, не побочный эффект вызова bro.

Bro и Matt Pack поставляются одним инструментом. Навыки находятся в соседних каталогах. Перед применением прочитай фактический `SKILL.md` выбранного навыка и указанные там материалы. Используй штатный вызов навыка, если host его предоставляет; при работе по инструкции из файла соблюдай её условия и границы пользовательского поручения. Не выдумывай отсутствующий API. Особенности Codex и Claude описаны в [host-вызовах](references/host-usage.md).

Заполнение документов и интервью не требуют создания задачи Jira: без выбранной задачи сохраняй решения в диалоге по разделу 2. Полный запуск приложения и всех тестов не является условием быстрой проверки; проверки полной ревизии определяются её инструкцией.

## 2. Определи поручение и задачу

**Сначала работа, затем предложение записи.** Если пользователь даёт задание, но явно не просит создать задачу Jira, сначала выполни задание. Новую задачу не создавай и не предлагай её создание до завершения работы, в том числе через вызываемые навыки. После завершения напиши: «Если хотите, зафиксирую выполненную работу в задаче Jira». Создай запись только после согласия пользователя. Это относится и к мелким изменениям, прототипам, вопросам «что если» и спонтанным идеям. Если пользователь уже указал существующую задачу, веди её в пределах поручения; дублирующую задачу и повторную фиксацию не предлагай.

- **Пустой вызов:** сначала выполни маршрутизацию раздела 1. Если начата полная ревизия, заверши её перед подбором задач. Иначе найди по известным соглашениям проекта доступные задачи без нерешённых блокеров; предупреждение о возрасте документов само по себе этому не мешает. Если правила трекера неизвестны, сначала уточни их. При наличии активных спринтов начни с них, иначе используй бэклог. Предложи выбор пользователя.
- **Ключ или ссылка:** прочитай выбранную задачу целиком — описание, статус, комментарии, метки, связи, маршрут и подтверждения прогресса. Карточка поиска не заменяет контекст.
- **Задание без задачи:** выполни поручение в контексте проекта, сохраняя первоначальную просьбу и уточнения в диалоге. Поиск или создание задачи в трекере не является предварительным этапом работы.
- **Явная просьба создать задачу:** найди похожие задачи, чтобы избежать дублей. Неочевидное совпадение обсуди до изменения существующей задачи; при отсутствии подходящей создай новую по просьбе пользователя. Первоначальную просьбу сохрани дословно, уточнения отдельно.
- **Вопрос вне доработки:** выполни запрошенный результат в контексте проекта. Прямой ответ не требует искусственной задачи на реализацию.

Трекер и формат задачи определяются соглашениями проекта. Для локального трекера используй его файлы; для внешнего — доступную интеграцию. После однозначного выбора веди маршрут, прогресс и статус в пределах поручения. Для внешнего трекера используй штатный переход статуса, для локального — установленный формат. Частичное поручение не отменяет оставшиеся критерии общей задачи.

## 3. Проверь готовность к работе

Восстанови нужный результат, границы, подтверждённые факты, существенные предположения, следующий шаг, последствия ошибки и способ проверки. Доступные факты выясни сам. Уточняй только неизвестное, которое меняет результат или существенное решение; уже известное повторно не спрашивай.

### Готовность к реализации ПО

Для новой разработки, багфикса и рефакторинга до реализации нужны два результата, сохранённые вместе с фактическим согласованием пользователя:

1. **Бизнес-сценарии:** акторы и цели, реальные или явно предлагаемые входы, права, исходные состояния, основной ход, существенные альтернативы, отказ/повтор, наблюдаемый итог и проверка. Сверь покрытие с требованиями и инвентарём акторов, входов и состояний. Для багфикса покажи текущее и исправляемое поведение; для рефакторинга — сохраняемое.
2. **Концептуальный дизайн:** минимально достаточные существующие, изменяемые и новые элементы, их реальные или предлагаемые имена, ответственность, входы/выходы и взаимодействие. Свяжи их со сценариями и исходниками. Объясни переиспользование и необходимость новых элементов; произвольные абстракции для будущих задач не добавляй.

Сценарии должны быть конкретны, проверяемы, достижимы при известных ограничениях, учитывать сбои и иметь триггер начала и условие завершения. Численные сроки/SLA уточняй, когда они существенны, вместо выдумывания числа ради шаблона.

Покажи оба результата и получи согласование каждого; один явный ответ может согласовать оба. Сохрани редакцию и ответ по [формату записей](references/work-records.md#готовность-к-реализации). Готовность требует полноты обоих результатов в согласованных границах; статус «в работе» и отсутствие возражений её не подтверждают. До этого разрешены чтение, диагностика, исследование, интервью и проектирование в пределах поручения.

При продолжении используй актуальные согласованные материалы. Повторное интервью и согласование неизменного решения не нужны. Существенно изменившийся сценарий, границы или ответственность требуют обновить и согласовать затронутую часть до зависимой реализации. Исследование или документация как самостоятельный результат сохраняют свои критерии; программный дизайн для них не выдумывай.

## 4. Восстанови или выбери маршрут

Пригодный сохранённый маршрут имеет приоритет. Сверь предпосылки и доказательства выполненного, затем продолжи следующий невыполненный шаг. Перед реализацией проверь раздел 3; отсутствующую подготовку добавь, сохраняя подтверждённую работу.

Если маршрута нет, оцени пять признаков: локальность области, определённость результата, простота связей, наличие установленного решения и однозначность проверки. Когда все простые, выполни поручение сам с нужными навыками и запиши короткий маршрут. Иначе передай `ask-matt` в отдельный доступный контекст цель, границы, факты, решения, критерии и реально доступные навыки. Его задача — выбрать маршрут до запрошенного результата. При отсутствии делегирования прочитай и примени его workflow в текущем контексте, явно указав ограничение.

До исполнения сохрани сложный маршрут по [формату записей](references/work-records.md#маршрут). Для каждого шага укажи результат и проверку. Если факты опровергли предпосылку маршрута, пересмотри его через `ask-matt`; изменение продуктовых границ согласуй с пользователем. Известные готовые решения не пересогласовывай.

## 5. Исполняй и сохраняй контекст

Связанные этапы обсуждения сохраняй в одном контексте. Независимое ограниченное поручение можно передать доступному субагенту: укажи согласованные сценарии, дизайн, критерии, доказательства согласования, файлы, права и способ проверки. Соблюдай действующую политику делегирования host/проекта; фактическая недоступность субагентов не разрешает заявить независимую проверку выполненной. Родитель координирует исполнителей и принимает результат по доказательствам.

До `grill-me`/`grill-with-docs` выбери место для интервью: указанную пользователем существующую задачу, явно запрошенную новую или текущий диалог, если задача не выбрана. Создание задачи обсуждения само по себе не разрешает реализацию. Сохраняй вопросы, рекомендации, фактические ответы и поправки по [формату интервью](references/work-records.md#интервью). Проверь запись перед передачей `to-spec` или следующему исполнителю; для выбранной задачи ссылка на файл не заменяет текст ответов, если соглашения требуют запись в трекере.

Оставайся собеседником: передавай вопросы и ответы без потери смысла. Ожидание обязательного ответа оставляет зависимый шаг незавершённым; независимую разрешённую работу можно продолжать.

После проверенного шага сохрани результат, связанные материалы, выполненные проверки, ограничения и следующий шаг по [формату прогресса](references/work-records.md#прогресс). Для кода используй согласованные публичные границы тестирования и соответствующий навык; для исследования — первичные источники и выводы. Заявление исполнителя «готово» требует проверки.

Если сервис недоступен для уже согласованной записи в трекер, сохрани точный незаписанный материал и точку продолжения в разрешённом локальном месте по [формату продолжения](references/work-records.md#недоступность-трекера). Назови блокируемое действие. Вход через внешний сервис выполняй штатным способом текущего host, в рамках разрешённого плана; конфигурация или запуск login не доказывают доступ. После восстановления сверь записанное и сохрани только недостающее.

## 6. Заверши запрошенный результат

**Быстрое ревью стиля.** После выполнения задания или задачи, перед итоговым ответом, просмотри изменённый код и самостоятельно приведи его к единому общепринятому стилю соответствующего языка. Используй знания, полученные при обучении, и уже известные соглашения проекта; для этого прохода не загружай дополнительные гайды или навыки по код-стайлу и не обращайся в интернет. Ограничь правки стилем изменённого кода, сохраняя поведение; затем повтори затронутые проверки. Если код не менялся, этот шаг пропусти.

Сопоставь каждый критерий поручения с наблюдаемым доказательством и перечисли ограничения. Для программной задачи проведи предусмотренную независимую проверку; собственная проверка её не заменяет. Для отдельного поручения на промпт проверь поведение на примерах и получи предусмотренное согласование конкретной редакции.

Закрой задачу штатным способом только после выполнения всех её критериев. Частичный результат запиши, оставив остальное открытым. Финальный ответ содержит результат, проверки и конкретные причины незавершённого. Примеры границ и продолжения — в [сценариях](references/examples.md).
